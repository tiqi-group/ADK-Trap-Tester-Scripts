# Custom layouts and mappings

The Analysis and Interfaces panels draw pins on a sketch of a physical interface. Two
sketches are built in: the **DSUB-50** feedthrough and the **FPC ribbon**. Any other
interface (an interposer, a bond-finger ring, a trap's electrodes) is a **layout
file** you add yourself. How the interfaces of your setup are wired to each other is
described by a **mapping CSV**.

Both are plain files, so they can be written by hand, generated by a script, or
kept in a git repository.

## Where the files live

Layouts (`*.json`) and mappings (`*.csv`) are looked for in these folders, sub-folders
included:

* the **default location**: `layouts/` in the app data folder unless you chose
  another folder in [Settings](settings.md#custom-layouts--mappings);
* extra folders added in [Settings](settings.md#custom-layouts--mappings) or with
  **Folders…** in the Analysis and Interfaces panels;
* folders listed in the `TRAP_TESTER_LAYOUT_PATH` environment variable.

Every layout found appears in the layout selectors and every CSV in the mapping
selectors. When two files have the same name, the selector adds their folder name.
Files ending in `.loopback.json` are
[loopback board files](analysis.md#the-loopback-board-file), not layouts, and are
skipped.

**Import…** checks a file before copying it into the default location. A layout is
also normalised on the way in. An existing file is never overwritten; the copy gets a
`-2`, `-3`, … suffix. The extra folders are only ever read.

Layouts often contain device-specific geometry. Keeping them in the app data folder,
or in a private repository added as an extra folder, keeps them out of this
project's repository.

## How it fits together

* Every pad of every layout has an **address**, `(connector, pin)`: the tester
  connector (0 to 7) and the pin on it. This is what a measurement result and a mark
  in the Interfaces panel refer to.
* The built-in layouts are the tester's own interfaces, so their addresses are
  fixed. A DSUB-50 pad's address is its pin; an FPC conductor is translated to the
  DSUB pin carrying the same signal, which is why a mark on a DSUB pin also shows on
  the ribbon.
* A custom layout stores a **nominal** address for each pad, and usually a name for
  it on that interface, its `ident` (`A3`, `287`, `DC1`).
* A **mapping CSV** says, net by net, which address each name is wired to in a
  particular setup. Selecting it re-addresses the layout's pads. That is how a
  measurement taken at the feedthrough lands on the right trap electrode.

## Layout file

A complete, small example: two DC electrodes and an RF electrode.

```json
{
  "schema": 2,
  "name": "My trap",
  "slug": "my_trap",
  "units": "mm",
  "pin_space": "dsub_pin",
  "match_by": "ident",
  "background": [
    {"kind": "rect", "x": 2.0, "y": 0.0, "w": 6.0, "h": 3.0, "style": "outline"},
    {"kind": "text", "x": -0.8, "y": 1.8, "text": "My trap", "ha": "left", "style": "caption"}
  ],
  "slots": [
    {"connector": 0, "pin": 1, "ident": "DC1",
     "shapes": [{"shape": "rect", "x": 0.0, "y": 0.0, "r": 0.4}]},
    {"connector": 0, "pin": 2, "ident": "DC2",
     "shapes": [{"shape": "rect", "x": 1.0, "y": 0.0, "r": 0.4}]},
    {"connector": 0, "pin": 3, "class": "rf", "label": "RF",
     "shapes": [{"shape": "poly", "points": [[2.5, -0.5], [4.5, -0.5], [4.5, 0.5], [2.5, 0.5]]}]}
  ]
}
```

### Top level

| Field | Required | Meaning |
| --- | --- | --- |
| `schema` | yes | Always `2`. Files without it, or with another number, are rejected. |
| `name` | yes | Display name, shown as the drawing's title. Can be changed freely. |
| `slug` | yes | Stable key of the interface: lower case, letters, digits and `_`. A mapping CSV's column for this interface must have this header, and a loopback board's `interface` must name it. Do not change it once mappings use it. |
| `match_by` | yes | How a mapping finds this layout's pads: `"ident"` (by name, for custom interfaces) or `"connector_pin"` (by address, used by the built-in DSUB-50 and FPC). |
| `pin_space` | yes | Which numbering `pin` is in: `"dsub_pin"` (1 to 50) or `"fpc_conductor"` (1 to 51). Custom layouts normally use `"dsub_pin"`. |
| `units` | yes | `"mm"` or `"grid"`. Only a label: the view scales the drawing to fit and keeps circles round. |
| `pitch_mm` | no | The grid pitch in mm, when `units` is `"grid"` and the pitch is known. |
| `background` | yes | Decoration that never changes: outlines, captions, labels. |
| `slots` | yes | Every pad, signal or not. |

### Slots (pads)

| Field | Required | Meaning |
| --- | --- | --- |
| `connector` | yes | Tester connector of the pad's nominal address. |
| `pin` | yes | Pin of the nominal address, in `pin_space`: the physical pin, 1 to 50 for a DSUB. |
| `ident` | when `match_by` is `"ident"` | The pad's name on this interface, as the mapping CSV writes it. Must not contain a comma. |
| `class` | no | What the pad is. Default `"signal"`. See below. |
| `label` | no | Text drawn in the pad. Without it the `ident` is drawn, or else the pin number. |
| `shapes` | yes | The pad's outline: one or more shapes. |

A pad drawn as several shapes, such as an electrode net made of several separate
segments, is one slot with several `shapes`. All of them take the pad's colour, and
clicking any of them marks the whole net.

Each shape is one of:

| `shape` | Fields |
| --- | --- |
| `circle` | `x`, `y` (centre), `r` (radius) |
| `rect` | `x`, `y` (centre), `r` (half the side), `rot` (rotation in degrees) |
| `finger` | `x`, `y`, `r`, `rot`: an elongated pad, as on a bond-finger ring |
| `poly` | `points`: the outline as `[[x, y], …]` |

`y` points **up**, as on paper.

### Pad classes

Only `signal` pads take a measurement or a mark; every other class is drawn in a fixed
colour, appears in the legend and ignores clicks.

| `class` | Legend |
| --- | --- |
| `signal` | (coloured by verdict or mark) |
| `gnd` | GND |
| `rf` | RF lines |
| `loopback` | Loopback |
| `sensor_heater` | Sensor / Heater |
| `axialisation` | Axialisation |

An unknown class is drawn grey.

### Background

Each entry has a `kind`, its geometry and a `style`. There are no colours in a layout
file: the style picks them, as the class does for pads.

| `kind` | Fields |
| --- | --- |
| `circle` | `x`, `y`, `r` |
| `rect` | `x`, `y` (centre), `w`, `h`, `rotation` |
| `line` | `x1`, `y1`, `x2`, `y2` |
| `polyline` | `points` (`[[x, y], …]`), `closed` |
| `text` | `x`, `y`, `text`, `ha` (`left`, `center`, `right`), `va` (`top`, `center`, `bottom`, `baseline`), `rotation` |

| `style` | Use |
| --- | --- |
| `outline` | Connector shells and board outlines (the default for shapes). |
| `hairline` | Thin guide lines. |
| `caption` | Titles and notes (the default for text). |
| `grid_label` | Small row and column labels. |

### Pads whose wiring is unknown

Sometimes a layout knows where its pads are but not which tester pin each reaches;
only the mapping knows. Write such pads with `"pin": 0`. When a generator calls
`assign_synthetic_addresses` (see [Generating a layout](#generating-a-layout)), each
gets a distinct **placeholder address** on connector 900 or above, which can never
be confused with a real pin. The pads can then be drawn and marked, and the
Interfaces panel warns that they are on placeholder addresses until a mapping wires
them.

## Mapping CSV

```text
connector,pin,my_trap,interposer
0,17,DC1,A3
0,18,DC2,B7
```

* The columns `connector` and `pin` (also accepted: `dsub_pin`) hold the tester
  address. Headers ignore case, spaces, `-` and `_`, so `Connector` and `DSUB Pin`
  work too.
* Every other column is one interface, headed by that layout's `slug`.
* Each row is one **net**: the net at that address is called `DC1` on `my_trap` and
  `A3` on `interposer`.
* A blank cell means the net has no pad on that interface. If a net has several pads
  on one interface, separate them with `;`.
* `pin` is the physical pin, 1 to 50.

Selecting the mapping re-addresses the pads of every layout it names: a layout with
`match_by` `"ident"` is matched by name against its own column, the DSUB-50 and FPC by
address. Pads the mapping does not name keep their nominal address.

Names are compared exactly, apart from surrounding spaces. A name that matches only
when ignoring upper and lower case is still used, but the Interfaces panel names it so
the CSV can be fixed. There is no further cleverness: `N04` and `N4` are different
pads. The banner above the view also lists the pads and CSV entries that found no
partner.

## Writing and checking a layout

For a small interface, write the JSON by hand, starting from the example above or from
a copy of an existing layout. Check that it loads:

```bash
uv run python -c "from trap_tester.core.layout import load_layout; print(load_layout('my_trap.json').name)"
```

or simply **Import…** it: a file that does not load is rejected with the reason.

### Generating a layout

For anything regular, or anything derived from another file (a pad list, a PCB
export), generate the JSON with a short script:

```python
from trap_tester.core.layout import (
    InterfaceLayout, Rect, Slot, assign_synthetic_addresses,
)

# Pads whose wiring only the mapping CSV knows get pin 0 ("unset")...
slots = [
    Slot(connector=0, pin=0, ident=f"DC{i}", x=float(i), y=0.0, r=0.4, shape="rect")
    for i in range(1, 11)
]
assign_synthetic_addresses(slots)  # ...and then distinct placeholder addresses

layout = InterfaceLayout(
    name="My trap",
    slug="my_trap",
    units="mm",
    pin_space="dsub_pin",
    match_by="ident",
    background=[Rect(x=5.5, y=0.0, w=11.0, h=2.0, style="outline")],
    slots=slots,
)
layout.save_json("my_trap.json")
```

`Slot` takes either `shapes=[SlotShape(...)]` or, for a single-shape pad, the
shortcut `x`, `y`, `r`, `rot`, `shape` used above; `pad_class` sets the class. The
built-in layouts are made the same way, by `core/layout/dsub50.py` and
`core/layout/fpc.py`.
